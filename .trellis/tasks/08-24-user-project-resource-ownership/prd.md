# 引入用户项目与项目级资源归属

## 目标与用户价值

让每个用户可以建立多个项目，并以项目作为应用及其 Kubernetes 资源的归属、隔离和清理边界。任何应用都必须且只能属于一个项目，从产品与数据层面消除孤儿应用。

GitHub 需求事实源：<https://github.com/cuihe500/Astro/issues/3>

## 已确认事实

- 系统尚未正式上线，除测试账号外没有其他用户；本次允许清理测试应用及其 Kubernetes 资源后进行破坏性模型变更，无需兼容存量数据。
- 当前 `App` 直接保存 `UserID` 与 `Namespace`，尚无项目模型或项目外键（`internal/model/model.go:44`）。
- 当前创建应用时统一使用 `astro-user-<用户 ID>`，因此同一用户的全部应用共享一个 Namespace（`internal/service/app.go:50`）。
- 当前应用 API 是 `/api/v1/apps` 下的扁平资源，所有权通过登录用户 ID 校验（`internal/handler/app.go:306`、`internal/service/app.go:212`）。
- Kubernetes 适配器已经以 Namespace 参数创建和操作 Deployment、Service，并可按需创建 Namespace（`internal/k8s/adapter.go:44`、`internal/k8s/adapter.go:91`）。
- 当前数据库只使用 GORM `AutoMigrate`，没有独立迁移工具（`internal/repository/db.go:20`）。
- 当前 Web 界面只有应用列表、创建与详情流程，路由同样以 `/apps` 为中心（`web/src/app/router.tsx:66`）。

## 需求

### R1 项目所有权

- 一个用户可以拥有多个项目。
- 新用户初始没有项目，系统不得自动创建默认项目。
- 用户必须显式创建项目后，才能部署 Pod 或创建应用。
- 每个项目必须且只能属于一个用户。
- 项目名称在同一用户内唯一，不同用户可以使用相同项目名。
- 不同用户不能读取或操作彼此的项目及项目内应用。

### R2 Namespace 映射

- 每个项目必须对应一个唯一且稳定的 Kubernetes Namespace。
- 同一项目内由 Astro 管理的 Deployment、Service 以及未来可能支持的 Ingress 等资源共享该 Namespace。
- 单个应用不独占 Namespace；用户也不再以单一 Namespace 作为所有项目的共同边界。
- 首版延续现有应用创建行为：创建一个 Deployment，并在配置端口时自动创建同名 Service。

### R3 强制应用归属

- 每个应用必须且只能属于一个有效项目，数据库不得保存无项目归属的应用。
- 应用名称在同一项目内唯一，不同项目可以使用相同应用名。
- 创建应用时必须指定当前用户拥有的项目；缺失、不存在或属于其他用户的项目均须拒绝。
- 应用查询、启停、重启、日志与删除必须同时满足登录用户对所属项目的所有权校验。

### R4 生命周期完整性

- 新建项目时建立或确保其 Namespace 可用；失败时不得留下可用但无对应 Namespace 的项目。
- 包含应用的项目禁止删除，并返回明确的项目非空业务错误；该操作不得删除任何数据库或 Kubernetes 资源。
- 仅允许删除空项目；删除成功后，项目记录及其 Namespace 均不得残留。
- 上线新模型前清理现有测试应用记录及其 Kubernetes 资源，不创建默认项目，也不迁移或兼容测试数据。

### R5 对外契约

- 项目提供最小的创建、列表、详情与删除能力。
- 首次交付必须包含项目列表、项目创建与空项目删除界面。
- 用户进入项目后，可以查看、创建及管理该项目内的应用；无项目时界面引导用户先创建项目。
- 应用 API 统一改为 `/api/v1/projects/:project_id/apps` 下的项目嵌套路由，详情、启停、重启和日志等操作继续嵌套应用 ID。
- 移除现有 `/api/v1/apps` 路由，不提供兼容别名。
- Web 路由与导航必须体现当前项目上下文，不能通过旧的扁平应用入口绕过项目归属。
- 所有 API 继续使用统一的 `code`、`message`、`data` 响应结构；外部输入在 handler 层校验。
- 新增项目相关错误码使用业务错误码分段并配置默认消息。
- API、架构说明及用户可见界面随最终范围同步更新。

## 验收标准

- [ ] 给定一个已登录用户，当其创建多个项目时，每个项目都有唯一且稳定的 Namespace。
- [ ] 同一用户不能创建重名项目，不同用户可以使用相同项目名。
- [ ] 新注册或现有用户在未显式创建项目时没有任何默认项目，也不能创建应用或部署 Pod。
- [ ] 给定两个不同用户，当一方请求另一方的项目或项目内应用时，API 拒绝越权访问。
- [ ] 当创建应用未提供项目、项目不存在或项目不属于当前用户时，API 返回对应统一错误响应，且数据库与 Kubernetes 均不产生应用资源。
- [ ] 当应用创建成功时，其项目外键非空，Deployment、Service 及后续 Ingress 等资源位于所属项目 Namespace。
- [ ] 同一项目不能创建重名应用，不同项目可以使用相同应用名。
- [ ] 应用列表、详情、启停、重启、日志和删除均按项目归属完成权限检查。
- [ ] 发布新模型前可验证地清理现有测试应用及对应 Kubernetes 资源，切换后数据库不存在无项目归属的应用。
- [ ] 删除非空项目时操作被拒绝，已有项目、应用和 Kubernetes 资源保持不变。
- [ ] 删除空项目成功后，其数据库记录与 Namespace 均不存在。
- [ ] 用户可在 Web 界面完成项目列表、创建和空项目删除，并在选定项目内查看、创建及管理应用。
- [ ] 无项目用户访问应用功能时会看到先创建项目的明确引导，不会出现可绕过项目归属的创建入口。
- [ ] 旧 `/api/v1/apps` 端点不可用；所有应用 API 均通过所属项目路径访问。
- [ ] 相关后端、前端与文档校验均通过 Makefile 中已有或随本任务明确新增的目标。

## 非范围

- 项目成员、邀请、跨用户协作或项目级角色权限。
- 多集群调度或跨 Namespace 项目。
- 任意 Kubernetes YAML/任意资源类型管理。
- 独立的 Service、Ingress 或其他 Kubernetes 资源 CRUD；待出现明确产品需求后另行设计。
- 为单个容器应用分配独立 Namespace。
- 自动创建默认项目或为测试数据提供兼容迁移。
- 级联删除非空项目及其应用。
- 保留旧 `/api/v1/apps` API 或 Web 路由兼容层。
- 未有当前产品需求的模板、配额、计费、环境分层或项目转让能力。
