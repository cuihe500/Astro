# 建立前端第一版本

## 目标

为 Astro 建立面向 C 端用户的第一版 Web 前端，以对外品牌 **BytCloud Auth** 提供主要注册/登录入口（内部 OAuth2 Provider 名称为 Authentik）、账号密码作为备选兜底，让不熟悉 Docker/Kubernetes 的用户可以在浏览器中完成“注册或登录 -> 创建应用 -> 管理生命周期 -> 查看日志”的最小闭环，并给后续前端开发留下清晰、克制的目录组织。

## 背景与已确认事实

- 当前仓库只有 Go/Gin 后端，没有前端工程或既有前端技术栈。
- 后端 API 基础路径为 `/api/v1`，统一返回 `code`、`message`、`data`；业务错误当前也使用 HTTP 200，前端必须以 `code` 判断结果。
- 本地账号支持注册和登录，作为 BytCloud Auth（内部 Provider 为 Authentik）不可用时的备选方案；登录成功同样返回 JWT 与用户 UUID，受保护接口使用 `Authorization: Bearer <token>`。
- 应用接口已支持列表、详情、创建、删除、启动、停止、重启和日志查询，并在服务端执行资源归属校验。
- 首版认证以 BytCloud Auth 为对外名称、以 Authentik 为内部 OAuth2 Provider；首次 OAuth2 登录由后端自动创建 Astro 本地用户和身份记录，已存在身份直接登录。
- Authentik 是否允许用户自助注册由 Provider 的 Enrollment Flow 决定，前端不复制一套注册流程；用户界面和对外文案不得展示 Authentik 这一内部名称，Provider 仍由后端配置决定是否启用。
- 后端当前没有 CORS 中间件，浏览器开发联调需要同源方案或前端开发代理。
- 产品面向非技术用户，界面应隐藏 Kubernetes 术语，优先呈现应用名称、镜像、副本、端口、状态和可执行操作。

## 需求

### R1. 工程与组织

- 前端作为仓库内独立工程组织，业务页面、通用界面、API 访问、认证状态和领域类型边界清晰。
- 提供统一的开发、构建、检查入口，并与仓库现有 Makefile 工作方式一致。
- API 地址允许通过开发环境配置切换，不把生产地址硬编码进业务代码。

### R2. 认证体验

- 未登录用户只能访问认证页面，登录成功后进入应用列表。
- 认证页首要操作是“使用 BytCloud Auth 继续”，同时覆盖已有用户登录和 Authentik Enrollment Flow 允许时的新用户注册；用户界面不展示内部 Provider 名称。
- 首次 OAuth2 callback 成功后，系统应建立 Astro JWT 会话；后端负责自动创建本地 User 与 OAuthIdentity。
- 支持本地用户名/密码登录和注册，但入口视觉上作为 BytCloud Auth 不可用或失败时的备选方案。
- JWT 会话在刷新后可恢复；Token 无效或过期时清理会话并返回登录页。
- 密码输入支持密码管理器、粘贴和显示/隐藏，不记录或展示敏感信息。
- BytCloud Auth 未启用、Enrollment Flow 不允许注册或回调失败时，用户仍可切换到本地账号流程，并能看到明确错误信息；技术日志和配置可保留 Authentik 名称。

### R3. 应用列表与创建

- 登录用户可以查看自己的应用列表，并清楚识别名称、镜像、状态、副本数和更新时间。
- 空列表提供直接的“创建应用”入口。
- 创建表单包含应用名称、镜像、副本数和端口，并在提交前提供与后端约束一致的基础校验。
- 创建成功后回到可见的应用状态；提交期间禁止重复提交。

### R4. 应用详情与生命周期

- 用户可以进入应用详情，查看应用基础信息和当前状态。
- 根据当前状态提供启动、停止、重启操作；操作期间显示进行中状态并防止重复触发。
- 删除应用必须二次确认，成功后返回应用列表。
- 用户可以请求并查看最近日志；日志区域保留换行、支持长行滚动，并提供重新加载。

### R5. 状态、错误与响应式

- 页面覆盖加载、空数据、请求失败和操作成功反馈，不出现无内容的空白界面。
- 错误消息优先使用后端统一响应中的 `message`，网络错误提供明确的重试路径。
- 支持桌面与移动浏览器，375px 宽度下无横向页面滚动，核心操作可通过键盘完成。
- 界面使用简体中文，采用安静、实用、适合重复操作的工作台布局，不制作营销落地页。

## 验收标准

- [ ] Authentik Provider 配置启用且 Enrollment Flow 允许注册时，新用户可通过 BytCloud Auth 首要入口完成 OAuth2 注册，首次回调自动创建 Astro 本地账号；已有用户可直接登录。
- [ ] 认证页将 BytCloud Auth 入口置于主要视觉层级，账号密码登录/注册作为明确但次要的兜底入口；用户界面不显示 Authentik 内部名称。
- [ ] BytCloud Auth 未启用、注册被 Provider 拒绝或回调失败时，用户可无损切换到本地账号流程并看到可理解的错误。
- [ ] 本地账号登录/注册成功后可建立会话，并在刷新页面后保持有效会话。
- [ ] 未登录访问受保护页面时会被引导到登录页；无效或过期 Token 会结束会话。
- [ ] 用户可完成应用列表、创建、详情、启动、停止、重启、删除和日志查看的完整流程。
- [ ] 所有 API 调用按统一响应 `code` 判断成功或失败，并展示可理解的错误信息。
- [ ] 创建、生命周期和删除操作不会因连续点击重复提交。
- [ ] 应用列表和日志至少具备加载、空数据、失败及重试状态。
- [ ] 关键表单具备可见标签、字段级错误和键盘可达的提交操作。
- [ ] 在桌面与 375px 移动视口下，页面无内容重叠或整页横向滚动。
- [ ] 前端具有可复现的开发、构建和检查命令，并记录目录组织原则。

## 范围外

- 应用模板市场、CPU/内存监控、自动扩缩容、持久化存储、域名和 TLS 管理。
- 用户资料、账号绑定、忘记密码、邮箱验证和多角色后台。
- 实时流式日志、WebSocket、复杂筛选分页、批量操作和离线能力。
- 暗色模式、自定义主题、国际化和原生移动端。
- 首版生产部署拓扑与 Kubernetes 发布清单；首版只保证可构建和本地联调。
