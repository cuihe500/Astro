# 代码规范合规审查设计

## 审查边界

以 `AGENTS.md` 为最高约束，以 `.trellis/spec/backend/` 为可执行细化规范。只审查当前仓库的后端实现、配置、构建入口和 Swagger 同步关系，不改业务代码。

## 判定方法

1. 建立文件清单和入口清单，确认所有 handler、middleware、service、repository、model、K8s adapter、配置和启动路径。
2. 用静态搜索定位高风险模式：忽略错误、标准库日志/打印、硬编码错误码、裸 SQL、直接跨层访问、缺少 binding/Swagger 注解、敏感字段和默认 secret。
3. 对每个命中阅读完整函数及其调用者，追踪请求、认证身份、资源归属、错误和响应的数据流。
4. 运行 Makefile 目标，区分源码失败、工具缺失、外部服务依赖和环境限制。
5. 对认证与 OAuth2 单独核对 state、provider、身份主键、email 冲突、token/secret 泄露和错误码契约。
6. 只把能够由代码、配置、命令输出或文档差异证明的内容列为发现；纯推测保留为残余风险，不冒充违规。

## 严重级别

- P0：可直接造成账号接管、跨租户访问、密钥/令牌泄露、数据破坏等重大风险。
- P1：认证失败、权限绕过、核心 API 错误传播/数据一致性故障或主要功能不可用。
- P2：明确违反项目规范，或会造成可观的运维、诊断、维护风险，但不构成立即重大安全事故。
- P3：低风险的文档、生成物、注释、格式或测试缺口。

## 报告结构

`report.md` 包含：审查结论、命令结果、按严重级别排序的发现、已验证的排除项、未验证/残余风险、建议整改顺序和审查时 Git 状态。每项发现使用固定字段：编号、级别、位置、规则、证据、影响、建议、验证状态。

## 兼容与取舍

- 测试缺口是否违规以现行规范的明确要求为准；历史遗留且规范明确标为已知技术债的项目单独标注，不扩大为新缺陷。
- 生成的 Swagger 文件若与源注解不同步，作为文档/发布风险报告；不把生成文件本身当作手写源代码审查。
- 设计判断类问题只提出建议，不在本任务内重写公共接口或移动分层职责。
