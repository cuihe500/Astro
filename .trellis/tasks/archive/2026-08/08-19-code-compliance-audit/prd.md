# 审查项目代码规范合规性

## 目标

识别当前 Astro 后端及其直接构建/接口文档中的不符合项，为维护者提供可复核的整改清单。审查默认只读取、验证和报告，不修改业务代码。

## 背景与已确认事实

- 项目规范来源为根目录 `AGENTS.md` 与 `.trellis/spec/backend/`。
- 项目为 Go + Gin + GORM + client-go 单仓库，当前仅配置 backend 规范层。
- 业务代码位于 `cmd/`、`internal/`、`pkg/`；配置位于 `configs/`；Swagger 产物位于 `docs/`。
- 当前仓库已有 OAuth2/OIDC 主认证实现及 `internal/service/oauth2_test.go`；规范文档仍说明历史上缺少测试，需以代码现状为准判断。
- 工作树在本任务开始前干净；本任务目录是当前唯一新增未跟踪内容。

## 审查范围

纳入：

- `cmd/server/`、`internal/`、`pkg/` 下的 Go 源码及测试。
- `configs/`、`Makefile`、`go.mod`。
- handler 注解与 `docs/` Swagger 生成物之间的直接一致性。
- 与上述代码直接相关的架构/规范文档中的可执行约束。

不纳入：

- `.git/`、Trellis 运行时代码及第三方依赖源码。
- 仅属未来规划、尚未实现的功能，不作为当前代码违规；若文档错误描述已实现能力，则记录为文档一致性问题。
- 纯风格偏好且不违反项目明确规范的意见。
- 未经用户另行要求的代码修复、重构、依赖升级或提交。

## 审查要求

- 按严重级别筛选真实违规：`P0`（可直接导致重大安全/数据风险）、`P1`（影响认证、租户隔离、错误处理或主要功能）、`P2`（明确规范违规或可维护性/可运维风险）、`P3`（低风险文档/格式问题）。
- 每项发现必须包含：严重级别、文件与行号、对应规范、代码证据、实际影响、最小整改建议。
- 先通过调用链和数据流确认行为，再将关键词命中列为违规；无法证明的内容标为待确认或不纳入结论。
- 覆盖输入校验、权限归属、统一响应、错误码与错误传播、错误返回值、日志及敏感信息、SQL 参数化、认证/OAuth2 状态校验、模型迁移、分层边界、Swagger、测试、Makefile 检查。
- 记录 `make build`、`make test`、`make lint`（若环境可用）和必要的 `make swagger` 结果；命令失败也要说明是代码问题、环境问题还是工具缺失。

## 验收标准

- [ ] 形成一份可复核的审查报告，所有 P0/P1/P2/P3 发现均带文件行号和规范依据。
- [ ] 对关键词搜索结果逐项去除误报，并说明关键排除项。
- [ ] 完成主要 handler → service → repository/K8s/auth 流程的跨层检查。
- [ ] 执行并记录 Makefile 规定的构建、测试、静态检查结果；无法执行的项目明确写出原因。
- [ ] 检查 OAuth2/OIDC 规范契约、敏感配置与 Swagger 同步状态。
- [ ] 审查期间不修改业务源码；如发现需要设计判断的整改，只报告证据和建议。
- [ ] 报告结论与当前 Git 工作树状态一致。

## 输出

审查结果写入当前任务目录的 `report.md`，最终回复摘要按严重级别列出，并附报告路径。
